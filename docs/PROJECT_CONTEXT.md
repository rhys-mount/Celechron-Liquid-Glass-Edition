## 一、项目定位与核心目标

## Celechron Liquid Glass Edition

基于浙江大学时间管理应用 Celechron 的高保真 Apple Liquid Glass 视觉适配版本。

Android 优先 · Apple 原生设计语言 · 业务功能完整保留 · 长期跟踪上游

### 1. 核心目标

我们决定从官方 Celechron 最新代码重新开始，制作一个视觉上接近 Apple iOS 26/27 Liquid Glass 系统应用的版本。

项目并不是重新开发 Celechron，也不是全面重构其业务架构，而是：

- 保留官方版的全部核心功能和原有信息组织。
- 主要改造导航栏、按钮、控件、主题、图标和视觉细节。
- 尽可能还原 Apple Liquid Glass 的材质、布局层次与交互体验。
- 保证内容可读性、Android 性能、稳定性和日常使用效率。
- 建立能够长期跟踪上游更新的代码结构与 Git 工作流。

项目的核心原则是：让 Celechron 看起来像一款原生 Apple 风格的应用，而不是给所有组件都加上毛玻璃。

### 2. 开发边界

我们明确决定：

- 不重新设计 Celechron 的主要业务逻辑。
- 不改变现有课程、任务、成绩、日程的数据模型。
- 不为了视觉效果牺牲内容密度、性能和可读性。
- 不盲目替换所有 Cupertino 组件。
- 不把旧 Liquid Glass 仓库的历史提交和代码直接搬过来。
- 不因视觉改造而降低后台刷新、通知、教务获取等原有功能的可靠性。

唯一已经明确要求移除的现有界面元素，是「接下来」页面的规划方案已过期提示横幅。底层的规划状态判断和更新机制仍需保留。

我们曾核对旧版与上游的差异：涉及约 67 个文件，增加约 1,234 行、删除约 566 行。这是决定从头重做的重要原因。

### 2. Git 分支策略

`main`：官方同步分支

`liquid-glass`：Edition 稳定版本和 GitHub 默认分支

`feat/*`：独立开发分支

确定的规则：

- `main` 尽量保持与官方上游一致，不混入自己的视觉修改。
- `liquid-glass` 负责保存可发布的 Liquid Glass 版本。
- 不同开发任务通过独立分支、独立提交和 PR 完成。
- 不随意改动上游仓库。
- 保留旧仓库，不删除或覆盖。
- 保留原项目 GPLv3 许可证、原作者和贡献者信息。

### 3. 官方更新如何同步

以后原版 Celechron 更新时：

1. 同步上游代码到自己的 `main`。
2. 通过独立 PR 将新代码合并到 `liquid-glass`。
3. 如果出现冲突，优先保留官方最新业务功能，并重新协调视觉适配。
4. 运行自动化测试和 Android 构建。
5. 验证通过后发布新版。

我们希望未来由 Codex 辅助完成这些工作，但不允许未经验证就自动合并可能影响功能的更新。

## 三、全局视觉设计规范

这是我们讨论最多、目前也最明确的部分。

### 1. Liquid Glass 使用范围

| 界面元素       | 确定方案                          |
| ---------- | ----------------------------- |
| 底部导航栏      | 标准悬浮式 Liquid Glass Tab Bar    |
| 顶部导航栏      | 尽量统一 Apple 原生 Liquid Glass 风格 |
| 顶部操作按钮     | 采用与 Liquid Glass 协调的原生风格      |
| 普通课程卡片     | 保留实体材质                        |
| 任务卡片       | 保留实体材质                        |
| 成绩和考试信息    | 保留实体材质                        |
| 设置分组列表     | 保留系统实体分组风格                    |
| 弹窗和菜单      | 按场景选择，整体不割裂                   |
| 页面背景       | 参考 Apple 系统应用默认背景             |
| 页面交互动画     | 保持统一、自然，不额外夸张                 |
| 加载、空白、错误状态 | 统一视觉表现，保留原有逻辑                 |

我们不追求所谓的“玻璃覆盖率”。

Liquid Glass 主要服务于浮动导航、操作层和必要的悬浮控件。内容层继续使用清晰的实体背景。

### 2. 底部 Tab Bar

这是最重要的视觉改造之一。

保留原有五个 Tab 和顺序：

接下来

日程

任务

学业

设置

具体要求：

- 直接采用标准 Liquid Glass Tab Bar，不做额外的个性化视觉设计。
- 保留原有 Tab 切换、页面滑动和页面状态。
- 采用自然的触摸反馈和选中动画。
- 页面内容可以在玻璃导航栏后方滚动。
- 最后一项内容必须完整可见、可点击。
- 不硬编码底部导航栏高度或安全区。
- 关闭 Liquid Glass 后恢复标准 Cupertino 导航栏。

### 3. 顶部 Navigation Bar

尽可能统一 Apple 原生设计语言：

- 优先使用 Large Title。
- 页面滚动时支持自然的大标题收缩。
- 顶部操作按钮采用统一的 Liquid Glass 风格。
- 根据页面实际需求允许紧凑布局。
- 避免为了统一而修改原有功能组织。
- 二级页面也要保证导航样式协调。

统一的是设计语言，不是要求所有页面使用完全相同的组件布局。

### 4. 背景与排版

我们决定：

- 采用 Apple 系统应用风格的浅色与深色背景。
- 不增加装饰性渐变背景、壁纸或额外纹理。
- 不强制移植 San Francisco 字体。
- Android 继续使用系统字体。
- 参考 Apple 排版规范统一字号、字重、标题层级和间距。
- 数字、时间等信息重视对齐与可读性。
- 保留系统字体缩放和无障碍支持。

### 5. 图标体系

应用内部图标尽量采用 Cupertino 风格，参考 SF Symbols 的视觉语言。

要求：

- 尽量保持线性图标风格一致。
- 统一视觉尺寸、描边粗细和选中状态。
- 优先使用 Cupertino Icons。
- 缺少合适图标时采用风格协调的替代资源。
- 避免明显混用 Material 与 Cupertino 风格。
- 不直接依赖 Apple 专有的 SF Symbols 图标资源。

## 四、颜色与主题

### 1. 主题模式

保留 Celechron 原有的三种模式：

- 跟随系统
- 浅色
- 深色

Liquid Glass 必须遵循应用的实际主题设置，而不是单纯读取 Android 系统主题。

旧版曾出现过系统深色、App 浅色时图标反色，以及切换亮暗模式导致页面黑屏的问题，因此这一点要作为重点回归测试。

### 2. 求是蓝配色

求是蓝

浅色模式

\#003F88 · 已确定

亮蓝色变体

深色模式

\#5B9BEE · 候选，尚未最终确定

最终决定是：

- 浅色模式强调色使用浙大求是蓝 `#003F88`。
- 深色模式使用同色系、亮度更高且对比度足够的蓝色。
- 深色模式的精确色值需在实际界面中测试后确定。
- 普通正文、标题仍使用系统语义文字颜色。
- 不把所有控件、卡片或玻璃材质染成蓝色。
- 不使用 Android 壁纸动态取色替换品牌色。

### 3. 语义颜色

课程类别、日程类型和任务状态原有的颜色区分全部保留。

求是蓝只负责品牌强调与主要交互，不代替其他信息类别颜色。

深色模式可以针对对比度适度优化这些语义色，但不改变它们原本代表的含义。

## 六、Liquid Glass 开关与性能策略

这一部分也已经决定。

### 1. 用户设置

在「设置 → 外观」增加一个：

Liquid Glass 总开关

默认开启。

关闭后：

- 恢复标准 Cupertino 导航和交互控件。
- 页面功能和数据不变。
- 用户的开关选择会被持久化。
- 重启应用后继续保持设置。

### 2. 画质控制

不提供手动画质档位。

我们已经否定了「自动 / 高画质 / 省电」这类用户可见设置。

底层允许使用自动画质调整和硬件能力检测：

- 支持高质量渲染时使用合适的玻璃效果。
- 性能不足时降低渲染质量。
- 无法稳定渲染时采用简化效果或 Cupertino 回退。
- 不能因视觉效果造成黑屏、无法点击或应用崩溃。

自动画质和总开关是两个不同机制。

### 3. 动画

不人为增加夸张动画，也不刻意削弱 Liquid Glass 本身的交互效果。

标准是：

- 与 Apple 原生交互风格接近。
- 不同页面、控件的动画节奏统一。
- 滑动和点击反馈自然。
- 尊重系统减少动态效果等无障碍设置。
- 不因动画影响实际操作效率。

## 七、平台优先级与适配策略

| 平台         | 优先级 | 目标                |
| ---------- | --- | ----------------- |
| Android 手机 | P0  | 主要开发和验收平台         |
| Android 平板 | P1  | 重点适配横屏            |
| Windows    | P2  | Android 稳定后，有精力再做 |
| iOS        | 暂缓  | 尽量保留兼容性，不作为首轮重点   |

### 1. Android 手机

Android 是项目最重要的运行平台。

使用 Flutter 自身的 Shader 实现 Liquid Glass，而不是依赖 UIKit / SwiftUI 原生玻璃控件。

需要适配：

- Edge-to-Edge 布局。
- 透明系统状态栏及正确图标颜色。
- 手势导航和传统三键导航。
- 刘海屏、挖孔屏与安全区。
- 输入法弹出时的布局。
- 系统返回手势。
- 不同刷新率和 GPU 性能。
- 浅色、深色及字体缩放。

我们已经确认不为了 Liquid Glass 主动提高原版最低 Android 版本要求。

目前官方项目最低 Android 版本为 API 28（Android 9）。

### 2. Android 平板

你平时主要使用平板横屏，所以我们决定以横屏为主要适配场景。

参考 iPadOS 的 Sidebar 和 Split View。

规划方向：

- 手机保留底部 Liquid Glass Tab Bar。
- 平板横屏优先考虑侧边导航栏。
- 侧边栏能够根据屏幕空间收缩。
- 内容区域利用大屏空间，但不过度拉伸卡片。
- 在适合的页面采用列表与详情并排的 Split View。
- 课程、日历等场景可考虑多栏布局。
- 保留分屏、自由窗口的兼容性。
- 平板竖屏以兼容为主。

这些属于已经确定的设计方向，但具体断点、导航组件和 Split View 实现还没有定稿。

### 3. Windows 与 iOS

Windows 暂不进行专门开发，后续有时间可以尝试桌面化适配。

iOS 不作为第一阶段构建和测试的硬性目标，但尽量避免在 Flutter 层引入不必要的平台依赖。

### 3. 代码架构原则

保留原有 GetX + Hive + Cupertino 架构，单独封装 Liquid Glass 视觉层。

- 顶部导航。

- 原有业务回调行为。

不能为了切换主题而重新创建整个 `GetCupertinoApp`，也不能使用硬编码的 Tab Bar 高度来解决布局问题。

## 最终总结

我们已经完成了 需求讨论和第一阶段工程审查，而不是已经完成 Liquid Glass 开发。

项目目前有三个明确的长期方向：

视觉上： 尽可能还原 Apple 系统应用的 Liquid Glass 体验，求是蓝作为品牌识别，统一而克制。

工程上： 保留 Celechron 原有业务架构，建立独立的视觉适配层，确保性能、稳定性与可维护性。

维护上： 真正 Fork 官方仓库，定期同步上游功能，不因为修改界面而与官方代码长期脱节。

接下来最重要的事情不是继续讨论新的视觉细节，而是解决 Android 构建基线，再开展底部 Liquid Glass Tab Bar 的最小可运行验证。

这份总结可以作为我们后续整个项目的需求基线。即使未来开启新对话，只需要提供这份内容及 Codex 最新开发报告，就能恢复主要设计决策、技术约束和项目进度，不必重新讨论一遍。
